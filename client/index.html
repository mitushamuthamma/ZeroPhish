Why Adversary-in-the-Middle (MitM) Relays Fail

In traditional authentication, phishing tools like Evilginx proxy requests and trick victims into entering passwords and 6-digit 2FA codes, which are instantly relayed to the authentic server.

With ZeroPhish, the victim’s browser calculates the signature directly over window.location.origin. Because the victim is on the fake site (http://localhost:5001), the signature is mathematically bound to that fake domain. The authentic server on port 5000 immediately detects the mismatch and rejects authentication (wrong_domain).

Architecture & Protocol Comparison

Why cryptographic origin binding is the only permanent solution to modern phishing relays.

Passwords & 2FA (SMS/TOTP)

  • Vulnerable to Evilginx relays: Attacker proxies the login page; user hands over password & OTP code in plaintext.
  • Shared secrets: If server password hash database is breached, user credentials can be cracked offline.
  • No Origin Knowledge: A 6-digit OTP code has no idea what URL bar it was entered into.
Vulnerable to Modern Phishing

ZeroPhish (Passkey Security)

  • Immune to Phishing Relays: The browser automatically includes window.location.origin inside the cryptographic signature.
  • Zero Shared Secrets: Server only stores 65-byte public keys. Database leaks reveal zero credentials.
  • Zero Replay Window: Challenges are single-use nonces cryptographically invalidated upon first check.

03 — Beyond Login

A stolen session cookie is not enough

Once you're logged in, most systems just hand out a session cookie that can be stolen and reused without ever needing the private key again. ZeroPhish extends domain-bound signing across the whole system, not just the login step.

1 Sign sensitive actions

Changing a password, editing email, or transferring funds require a fresh signature at the moment of the action — not just a valid cookie.

2 Time-limited, one-use signatures

Every signature expires quickly (30s) and burns immediately upon first check, closing the door completely on replay attacks.

3 Bind sessions to the key

Sessions in the database are tied to the verified public key itself, so a stolen cookie alone isn't enough to act as the user.

4 Scoped permissions

A signature made for changing an email can't be reused to perform a wire transfer or administrative action (nonce purpose-bound).

5 Anomaly detection

Repeated failed verifications, fake relay traps, or rapid registration floods are flagged and automatically placed into quarantine lockout.

6 Secure the registration step

Domain-binding can't protect the very first signup, so a secondary confirmation check (6-digit email confirmation code) is enforced there.

7 Encrypt stored data

Sensitive actions (transfer amounts, recipient addresses) are encrypted with AES-256-GCM. Even if the server database leaks, sensitive data doesn't leak in plain text.

Net effect
A stolen cookie alone is now powerless — sensitive actions still demand fresh proof from the device's private key.

Cryptographic Formulas

Registration: Public_Key = ECDSA_P256_UncompressedPoint(Client_PrivateKey)
Authentication: Signature = Sign(Client_PrivateKey, Nonce + "|" + Origin)
Sensitive Action: Signature = Sign(Client_PrivateKey, Nonce + "|" + Origin + "|" + Action + "|" + Details)
Database At-Rest: Ciphertext = AES_256_GCM_Encrypt(ServerKey, Nonce_12B, Action_Details)
